# F2S-004 — Evidence-bound FBX mapping packages

## Scope

`FbxMappingPackage.v1` is an additive binding envelope for an existing accepted
`FbxStagedMapping.v1` or `FbxStagedMapping.v2` manifest. It does not create a
new mapping language or change component, port, connectivity, family, source-
graph, or native StagedJSON semantics.

The package binds one mapping approval to:

```text
exact FBX input bytes
accepted committed ufbx WASM and provenance
canonical FbxSourceGraph.v2 bytes
canonical embedded mapping bytes
```

Bare v1 and v2 mapping manifests remain supported as
`UNBOUND_LEGACY_MAPPING`. Their source-graph, mapping-ledger, StagedJSON, and
conversion-report artifact bytes are unchanged.

## Contract

The executable Draft 2020-12 schema is:

```text
contracts/fbx/fbx-mapping-package.v1.schema.json
```

The closed package shape is:

```text
schema = FbxMappingPackage.v1
packageId
source { sha256, byteLength, fbxVersion }
parser { wasmSha256, upstreamRevision, sourceSha256, provenanceSchema }
sourceGraph { schema = FbxSourceGraph.v2, canonicalSha256 }
mapping { schema, canonicalSha256, manifest }
```

`mapping.manifest` is the original v1 or v2 mapping object. Package generation
canonicalizes it for hashing but does not rewrite or semantically upgrade it.
The existing mapping validator still governs the manifest after all binding
checks pass.

## Canonical hash authority

All digest values are lowercase SHA-256.

| Evidence | Hashed bytes |
|---|---|
| source | exact FBX bytes |
| parser | exact committed `fbx_parser.wasm` bytes |
| source graph | UTF-8 bytes of existing `canonicalJson(FbxSourceGraph.v2)` |
| mapping | UTF-8 bytes of existing `canonicalJson(mapping.manifest)` |
| package ID | UTF-8 bytes of existing `canonicalJson(package payload)` |

The package-ID payload contains `schema`, `source`, `parser`, `sourceGraph`, and
`mapping`, and excludes only `packageId`. Filenames, paths, timestamps, locale,
random values, host identity, and object insertion order do not enter the hash
boundary.

## Runtime gate

Package mode evaluates authority in this order:

```text
package structural validation
→ exact source-byte binding
→ committed parser/WASM binding
→ existing parser execution
→ canonical FbxSourceGraph.v2 binding
→ embedded mapping and package-ID binding
→ existing mapping semantic validation
→ existing port/connectivity/family validation
→ existing native StagedJSON writer
```

Successful package conversion records:

```text
SOURCE_BINDING_PASS
PARSER_BINDING_PASS
PARSE_PASS
SOURCE_GRAPH_BINDING_PASS
MAPPING_BINDING_PASS
PACKAGE_ID_PASS
MAPPING_PASS
STAGEDJSON_PASS
```

Binding failures are classified independently as:

```text
BLOCKED_SOURCE_BINDING
BLOCKED_PARSER_BINDING
BLOCKED_SOURCE_GRAPH_BINDING
BLOCKED_MAPPING_BINDING
```

Existing mapping, parse, transform, and StagedJSON-contract statuses remain
separate. Package mode never falls back to an unbound mapping after a binding
failure.

## Artifacts

A successful package conversion emits the existing four artifacts plus:

```text
<base>.fbx-binding-report.json
```

The report records expected and observed evidence, package identity, verified
schemas, ordered pass statuses, and the terminal status. It contains no machine
paths or timestamps.

A blocked package conversion never emits StagedJSON. It emits only source graph
or other evidence that was safely available before the failing gate.

## Deterministic package generation

Use:

```bash
node scripts/fbx/build-mapping-package.mjs \
  <source.fbx> <mapping.json> <output.fbxmap.json>
```

The tool uses the accepted Node parser adapter, committed parser provenance and
WASM, production source-graph construction, the existing mapping validator,
port resolver, and explicit-connectivity validator, and the production
package/hash modules. Repeated runs over identical repository state and inputs
produce byte-identical package JSON.

## Operator integration

The existing converter remains:

```text
fbx_to_stagedjson
```

Its secondary JSON input accepts either a package or a bare mapping manifest.
Package mode supports explicitly mapped `PIPE`, `ELBOW`, `TEE`, `REDUCER`,
`FLANGE`, and `VALVE` families. No mapping editor, catalog UI, bespoke tab,
preview, canvas, or downstream-format change is introduced.
