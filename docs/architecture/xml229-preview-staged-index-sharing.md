# XML229 strict Preview staged-DTXR index sharing — candidate G2 optimization

The source-worker engineering path previously parsed and indexed the same original staged JSON again for each strict Line List repair fragment. For K automatically/fuzzily matched branches, this could cause K strict index builds. Exact K, hot stage cost, and runtime performance on the Owner private dataset are NOT measured.

The new path caches a single staged DTXR index locally to the synchronous Preview call, solely across the branch fragments rebuilt under one strict config; it is never a cross-source or cross-basis global cache. The strict repair still removes fuzzy inherited Line List data and redoes branch and node evaluation. Core XML dryrun respects an optional internal runtime.stagedIndex parameter; if absent, original index construction remains unchanged.

The targeted strict test creates a fake index producer only in its temporary test directory to count calls and assert that two independent strict branch repairs use the same staged object, and that no matching repair does not build another strict index. This test alone does NOT prove full original XML and CII engineering parity.

Before integration: run actual full-checkout Node tests and real Chromium on public EF05 and Owner-selected source, check exact branch/node DTXR matched provenance, physical owner mapping, source/Final kg, geometry, materials and native Release HOLD; measure duration/peak memory; compare initial vs candidate. New Index port MUST NOT substitute for input-basis custody, real Worker independence or native physical-to-CII verification.

This PR changes only strict Preview performance, not independent Worker process ownership or actual JSON Source-of-Truth. The latter is a distinct G2/G3 work package; no output release authority.
