**Key non-equivalence:** GC-PW cryptographic basis identity is **not** LFJ source SHA. A checked source digest can be equal where exact UTF-8 bytes are equal; neither `basisId` nor engineering `sourceId` should be rewritten to LFJ `sourceId`. An original file with UTF-8 BOM, invalid UTF-8, or text-normalizing read path may have **different raw bytes** from a consumer's `TextEncoder`-derived string digest. Treat that as an explicit comparability status/typed error, never silently ignore/re-encode byte differences.

**Proposed future read-only seam (not authority or implemented API):**

```text
ConsumerSourceBinding.v1 {
  consumerDomain: 'xml-cii/2019',
  consumerSourceId: 'PL01',       // stable engineering file occurrence identity
  sourceRole: 'staged-json',      // not original XML / not combined XML
  sourceSha256: '<hex>',          // LFJ original byte custody SHA
  sourceRevision: '<generation>:sha256:<hex>',
  mediaType: 'application/json',
  basisId: '<optional existing GC-PW basisId after caller authenticates>'
}
```

**Rules:** never pass LFJ's `sourceId:sha256:...` in place of GC-PW `sourceId:PL01`; never infer that `stagedSourceSha256` matches raw bytes without checking encoding; no implicit `engineeringReady` or edit/export grant; keep source index distinct from XML original/combined occurrence IDs; preserve opaque source bytes even when semantic output is unsupported.
